# Hot reload

Current behavior as of 0.9.0: restart-based redeploy from 0.7.0 is restored. Both modes now trigger only when .java documents are saved in VS Code (including Auto Save/Save All), via onDidSaveTextDocument. Source filesystem change/create/delete watchers were removed; resource and POM saves do not trigger reload even with broad watch globs. Default watch is src/**. Captured per-instance epochs precede async canonical path resolution. Verification: 70 units and all five live integrations passed; VSIX 0.9.0 generated. The original 0.7.0 design/completion notes below are historical.

Approved request: HotSwap in debug plus optional automatic rebuild/redeploy, debounced and serialized. Implement per-instance hotReload {mode: hotswap|redeploy, delayMs:1000, watch:[src/**,pom.xml], exclude:[]}; absent means off. Configure Hot Reload and Apply HotSwap commands. File create/change/delete events are scoped to the real project, filter known outputs/control directories and generated POMs, and re-read the latest settings before running. Stop/trust loss/removal/shutdown cancel pending work. Changes while compiling coalesce to one follow-up; manual operations share the same instance operation guard. Automatic redeploy preserves whether the current runtime is debug and refuses publication if stopped, replaced or disabled while building.

HotSwap: require Red Hat Java language support and an owned Microsoft Java debug session; compile incrementally via java.execute.workspaceCommand/vscode.java.buildWorkspace, require success status 1, then customRequest(redefineClasses) on that exact session after checking generation again. No global Java settings changes. Method-body edits can work; structural edits should surface a clear failure and allow explicit Build and Debug. No automatic restart on HotSwap failure. No application execution outside the existing managed debug runtime.

Tasks: validated config/schema and pure reload filtering/debounce scheduler; generation-safe HotSwap adapter; VS Code watcher/commands and automatic build guard; tests for bursts, concurrent operations, failed compiles, invalidation, ignored outputs and multiple instances; real Java 8/17 method replacement and live Maven redeploy; docs, review and VSIX. This implementation rebuilds/restarts the configured Tomcat instance for redeploy (context state is lost); static-file copying/exploded deployment is deferred. Automatic save/reload runs only after the user starts a runtime and explicitly enables this feature.

Primary API references: https://code.visualstudio.com/docs/java/java-debugging ; https://github.com/microsoft/vscode-java-debug/blob/main/src/build.ts ; https://github.com/microsoft/vscode-java-debug/blob/main/src/extension.ts .

Completed: 70 unit tests and all five live integrations passed. JDI changed HTTP output on managed Java8/17 without replacing the JVM; the Maven integration grouped five events into one successful rebuild/restart and preserved the serving JVM after an invalid compilation. Reviewer concurrency findings addressed with invalidation epochs, signature/generation checks across awaits and a shared manual/automatic operation guard. VSIX 0.7.0 generated. VS Code UI/adapter/import behavior remains manual verification.
